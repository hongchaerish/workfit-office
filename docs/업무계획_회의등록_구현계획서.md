## 1. 목표

업무계획에서 회의·미팅을 **"회의 1건 = 캘린더 일정 1건 + 참석자"** 구조로 등록한다.

- 회의는 주최자가 한 번만 등록한다. 참석자는 각자 다시 적지 않아도 **자기 업무계획 칸과 캘린더에 회의가 보인다.**
- 같은 회의를 다른 사람이 또 등록하려 하면 **새로 만들지 않고 참석자로 합류**시켜 중복을 막는다.
- 본문 글자('회의'·'미팅')로 일정을 짐작해 만드는 방식은 이미 중단했다(2026-10-01 배포).
- 기존 자동 연동으로 쌓인 중복 일정을 정리한다.

### 성공 기준
1. A가 업무계획에서 B·C를 참석자로 회의를 등록하면, 캘린더에 회의가 **1건**만 생기고 A·B·C의 업무계획 칸에 회의 칩이 보인다.
2. B가 같은 날·같은 시간대에 비슷한 제목으로 회의를 등록하려 하면 "기존 회의에 참석자로 합류"가 제안되고, 합류해도 일정은 1건이다.
3. 회의 알림·리마인더가 §2에서 정한 대상에게만 간다(전 직원 발송 없음).
4. 모바일 웹(PWA) 업무계획에서도 같은 방식으로 회의를 등록할 수 있다(결정 e).

## 3. 현행 구조 확인 결과 (설계 근거)

| 항목 | 현황 | 이번 작업에 미치는 영향 |
|---|---|---|
| 일정 저장 | `calendarEvents` 컬렉션. `eventType`·`attendeeUserIds`는 Appwrite 속성이 없어 **메모 안 `[CAL_META:{…}]`로 인코딩** (`calendarEvent.repo.ts`) | 새 컬렉션·속성 없이 진행 가능 |
| 생성 알림 | `notifyRecipients`: 참석자 + 공개 범위 대상(**COMPANY면 재직자 전원**) | b 결정대로 회의는 참석자만 받도록 수정 필요 |
| 10분 전 리마인더 | Appwrite Function `calendar-reminder`: 소유자 + 공개 범위 대상(**COMPANY면 전원**). **참석자는 읽지 않음**(메모의 CAL_META를 해석하지 않음) | 참석자 해석 추가 + c 결정 반영 후 **함수 재배포**(개발 → 운영) |
| 수정 권한 | `update`/`remove`는 소유자만(`requireOwned`) | "참석자로 합류"는 소유자가 아니어도 **본인만 참석자에 추가**하는 전용 동작이 필요 |
| 업무계획 월간표 | 캘린더 회의를 **소유자 + 참석자 행**에 칩으로 투영(업무계획 유래 일정은 제외) | 표시는 대부분 재사용. 칩 클릭 시 회의 상세 연결만 추가 |
| 참석자 선택 UI | `CalendarEventModal`에 사원 검색·다중 선택 구현됨(웹·모바일 공용) | 회의 등록 창에서 재사용 |
| 회의실 | 자원예약 모듈(`reservation`)에 시간·참석자 필드 있음 | 4단계(선택)에서 연동 |

## 4. 설계

### 4.1 데이터
- **신규 컬렉션·속성 없음.** 회의 = `CalendarEvent { eventType: 'MEETING', attendeeUserIds, visibility: g 결정값 }`.
- 업무계획 본문에는 회의를 쓰지 않는다. 회의는 캘린더에만 있고, 업무계획 칸에는 칩으로 보인다(중복 원천 제거).

### 4.2 도메인 규칙 (`domain/calendarEvent/meeting.ts` 신규, 순수 함수·테스트)
- `findSimilarMeetings(events, draft)`: 같은 날짜 + 시간이 겹치거나(종일 포함) + 제목이 비슷한(공백·기호·`[회의]` 접두 제거 후 포함 관계 또는 일치율 기준) **회의**만 반환.
- `canJoinMeeting(actor, event)`: 볼 수 있는 회의이고 아직 참석자가 아니며 소유자가 아닐 때 true.
- `meetingNotifyTargets(event, policy)` / `meetingReminderTargets(event, policy)`: b·c 결정 규칙을 한곳에 둔다. 웹 알림과 리마인더 함수가 같은 규칙을 쓰도록 함수 쪽에 같은 로직을 옮긴다.

### 4.3 저장소 (`calendarEvent.repo.ts`)
- `joinAsAttendee(actor, eventId)`: `attendeeUserIds`에 **본인만** 추가. 다른 필드는 변경 불가. 주최자에게 "○○님이 회의에 참석합니다" 알림(선택).
- `leaveAsAttendee(actor, eventId)`: 본인만 빠지기.
- `notifyRecipients`: `eventType === 'MEETING'`이면 공개 범위와 무관하게 b 결정 대상에게만.
- 모두 기존 `exclusiveMutation`(직렬화) 안에서 처리해 동시 합류 경쟁을 막는다.

### 4.4 화면
1. **업무계획 리본 [회의 등록]** 버튼(편집 중인 칸의 날짜·작성자 기준).
2. **회의 등록 창**(`MeetingQuickModal`): 제목, 시작~종료(종일 선택), 참석자(검색·다중 선택), 공개 범위(기본 g), 메모.
   - 저장 전 `findSimilarMeetings` 결과가 있으면 목록을 보여 주고 **[이 회의에 참석자로 합류]** / [그래도 새로 등록] 중 고르게 한다.
3. **회의 칩 클릭** → 회의 상세(시간·주최자·참석자·메모). 주최자는 수정·취소, 참석자는 [참석 취소].
4. **모바일 PWA**: `MobileTaskScreen`에 같은 [회의 등록] 진입점과 상세 시트(결정 e).
5. (i 결정 시) 캘린더 상단 '부서·프로젝트' 필터 칩 제거.

### 4.5 리마인더 함수 (`appwrite/functions/calendar-reminder`)
- 메모의 `[CAL_META:{…}]`에서 참석자를 읽는다.
- 회의(`eventType` MEETING)는 c 결정 대상에게만 보낸다. 다른 일정은 현행 유지.
- 배포: `node scripts/deploy-calendar-reminder.mjs`(개발) → 확인 → `--prod`(운영, 별도 승인).

### 4.6 기존 연동 일정 정리 (h)
- 스크립트 `scripts/cleanup-workplan-sync-events.ts` 신규.
  - `--dry-run`(기본): 대상 건수·목록만 출력. 업무계획 원문 유무, 중복 묶음 표시.
  - 실행 모드: h 결정 범위대로 삭제. 삭제 전 대상 JSON을 로컬에 백업.
- 개발 DB에서 dry-run → 실행 → 확인 후, **운영은 dry-run 결과를 보고 별도 승인**.

## 6. 위험과 대응

| 위험 | 대응 |
|---|---|
| 전사 공개 회의가 전 직원 알림·리마인더를 유발 | 회의는 알림 대상을 공개 범위와 분리(§4.3·§4.5). 리마인더 함수 운영 배포를 웹 배포와 **같은 날** 진행 |
| 유사 회의 판정 오탐(다른 회의를 같은 회의로 제안) | 자동 합류하지 않고 **사용자가 고르게** 함. 판정 기준은 테스트로 고정 |
| 참석자 합류 동시 요청 | `exclusiveMutation` 직렬화. 이미 참석자면 무시(멱등) |
| 정리 스크립트 오삭제 | `[WP-SYNC:` 태그가 있는 일정만 대상, dry-run·백업 필수, 운영은 별도 승인 |
| 일정 컬렉션 전건 조회(규모 증가 시 느려짐) | 이번 범위 밖. 날짜·소유자 쿼리 전환은 별도 과제로 기록 |

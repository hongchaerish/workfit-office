### 1.2 데이터 모델

- **자원(`resources`)**: 분류(회의실·법인차량·공용장비·공용물품), 예약 방식(시간형 `TIME_SLOT` / 수량형 `QUANTITY`), 승인 방식(즉시 `INSTANT` / 승인 `APPROVAL`), 담당자, 슬롯 간격, 최소·최대 이용시간, 앞뒤 버퍼, 최대 사전예약일, 취소 마감, 운영시간, 상태(사용·점검·미사용).
- **예약(`resourceReservations`)**: 문서 ID `RSV-YYYYMMDD-NNNN`. 자원 코드·이름을 **스냅샷**으로 보관하고, 승인 방식도 신청 시점 값으로 고정(`approvalModeSnapshot`). 낙관적 잠금용 `version` 필드는 있으나 **쓰기 시 비교하지 않는다**.

### 1.3 상태 전이

```
            (INSTANT)                 종료시각 경과(읽을 때 파생, 저장 안 함)
 신청 ──────────────────► CONFIRMED ─────────────────────► COMPLETED
   │ (APPROVAL)               ▲   │
   ▼                          │   └──► CANCELLED (신청자: 마감 전 / 관리자: 언제든)
 PENDING ───── 승인 ──────────┘
   ├──── 반려(사유 필수) ──► REJECTED
   └──── 취소(사유 필수) ──► CANCELLED
```

- 점유 상태는 `PENDING`·`CONFIRMED`. 승인 대기도 시간을 막는다.
- 신청 검증 순서: 입력 형식 → 자원 사용 중 → 과거 시각 → 사전예약 한도 → 날짜 넘김 금지 → 슬롯 정렬 → 운영시간 → 이용시간 → 수량·인원 → 점유 충돌(버퍼 포함).
- 승인은 `315e6f5`부터 **점유 충돌만** 다시 본다(신청 후 자원 설정이 바뀌어도 확정 가능).

## 4. 개선안

### 4.1 1단계 — 안정화 (즉시, 데이터 유실 차단)

| 항목 | 내용 | 대응 |
|---|---|---|
| **① 운영 컬렉션 존재 확인** | prod Appwrite에 `resources`·`resourceReservations`가 있는지 먼저 확인한다(런북 §8 ②). 없으면 지금 운영 예약은 전부 저장되지 않고 있다. | C-1 |
| **② 저장 실패를 성공으로 숨기지 않기** | `crudBackend`의 404 폴백을 **쓰기에서는 오류로** 던진다. 읽기 폴백도 운영 빌드에서는 끄고 "컬렉션 미구성" 오류를 보여준다(개발 모드만 시드 허용). | C-1 |
| **③ 충돌 없는 ID 채번** | 생성은 `createDocument`만 쓰고(덮어쓰기 금지), 같은 ID가 있으면 409를 받아 번호를 올려 재시도. 또는 `RSV-YYYYMMDD-` + 무작위 접미사로 바꾼다. 화면에 보이는 번호는 유지 가능. | C-2, C-5 |
| **④ 자원 삭제 → 비활성화** | 삭제 대신 `INACTIVE` 처리. 진행·예정 예약이 있으면 삭제 버튼을 막고 "예약 N건 정리 후 삭제" 안내. 목록 삭제 버튼에 오류 표시 추가. | C-4, M-4 |
| **⑤ 저장소 권한 기본값 수정** | `canManageResources(actor, isAdmin = false)`로 바꾸고 호출부가 명시적으로 넘기게 한다. | S-2 |
| **⑥ 신청 권한 일관화** | `S_GW_RESOURCE.create`가 없으면 "+ 예약"·신청 탭·모바일 신청을 모두 막는다. | S-4 |

예상 규모: 파일 6~8개, 1~2일. 테스트: 동시 생성 ID 충돌, 404 쓰기 오류, 예약 있는 자원 삭제 차단.

   | 자원 점검·미사용 전환 | 영향받는 예정 예약 신청자 전원 | 〃 |
   | (선택) 시작 30분 전 | 신청자 | 〃 — 일정 리마인더 함수 재사용 |
2. **만료 상태 `EXPIRED`** (F-4) — 시작 시각이 지난 `PENDING`을 `COMPLETED`처럼 읽을 때 파생한다. 승인 화면에서 사라지고 내 예약에 "승인 기한 만료"로 표시.
3. **예약 변경** (F-3) — `reschedule(actor, id, {startAt, endAt, quantity})`. 자기 자신을 제외하고 신청 규칙 재검증. 승인형 자원은 다시 `PENDING`으로 되돌리고 담당자에게 알림.
4. **점검 전환 시 영향 안내** (F-2) — 자원을 점검·미사용으로 저장할 때 "예정 예약 N건이 있습니다. 함께 취소하고 알림을 보낼까요?" 확인 후 일괄 취소(사유 자동 기입).
5. **모바일 확장** (F-5, M-2) — 하단 탭에 "내 예약", 담당자에게만 "승인" 추가. 신청 폼은 데스크톱 `ReservationForm`의 입력 로직을 훅(`useReservationDraft`)으로 빼서 공유한다 — 같은 규칙을 두 번 구현하지 않는다.
6. **조회 범위 축소** (M-1) — 예약 현황은 보이는 기간(일·주)만 `Query.greaterThan('endAt', from)`·`Query.lessThan('startAt', to)`로 조회. 충돌 검사는 해당 자원·해당 일자만 조회. 내 예약은 `requesterUserId` 인덱스로 조회.

### 4.3 3단계 — 서버 측 보장 (운영 확대 전 필수)

1. **예약 쓰기를 Appwrite Function으로 이관** (C-3, C-6, S-1, S-3)
   - 생성·승인·반려·취소·변경을 함수 하나(`reservation-command`)로 모으고, 도메인 엔진(`engine.ts`)을 그대로 import해 서버에서 검증한다. 엔진이 순수 함수라 그대로 옮겨진다.
   - 함수 안에서 **자원 단위 잠금**(예: `resourceLocks` 문서에 `version` 증가 조건부 업데이트)으로 충돌 검사와 저장을 원자화한다.
   - 관리자 여부는 함수가 사용자 권한 그룹에서 직접 판정한다.
2. **컬렉션 권한 축소** — `resourceReservations`: 읽기는 로그인 사용자, 쓰기는 함수 전용(API 키). `resources`: 읽기 로그인 사용자, 쓰기 관리자 팀. 사용 목적 등 비공개 필드는 목록용 공개 뷰와 분리하거나 함수 응답에서 가린다.
3. 이 단계 전까지는 1단계 ③·④로 **덮어쓰기와 고아 예약만이라도** 막는다.

### 4.4 4단계 — 고도화 (선택)

| 기능 | 내용 | 비고 |
|---|---|---|
| 캘린더·회의 연동 (F-8, F-9) | 일정 등록 화면에서 회의실을 함께 선택 → 예약 생성, 참석자를 `attendeeUserIds`에 연결. 확정된 예약은 신청자 캘린더에 표시. | `업무계획_고도화_및_회의연동_개선안.md` §4와 같은 방향 |
| 빈 회의실 찾기 | 시간·인원을 먼저 입력하면 가능한 자원만 보여주는 역방향 검색 | 엔진 `validateReservationRequest`를 자원별로 돌리면 됨 |
| 반복 예약 (F-7) | 매주/격주 규칙 → 개별 예약 N건 생성(묶음 ID). 충돌 회차는 건너뛰고 결과 요약 | 최대 회차 제한 필요 |

## 6. 결정 사항 (2026-10-08 확정)

| # | 항목 | 결정 |
|---|---|---|
| 1 | 운영 컬렉션 | prod에 **존재함** — C-1은 현재 발생하지 않는다. 1단계 ② (404 폴백 오류화)는 공용 어댑터라 보류 |
| 2 | 예약 ID | **사람이 읽는 순번 유지**. 생성은 덮어쓰기 없는 `insert` + 충돌 시 다음 순번 재시도 |
| 3 | 자원 삭제 | (미결정 → 임시 적용) 예정 예약(대기·확정)이 있으면 삭제 차단, 없으면 삭제 허용 |
| 4 | 알림 | **이번에는 건드리지 않는다.** 알림 유형 정비와 함께 추후 한 번에 개선 |
| 5 | 시간 변경 | 승인형 자원은 **무조건 재승인**. 단, 확정 예약을 **기존 시간 범위 안으로** 바꾸면 승인 유지 |
| 6 | 서버 이관 | 3단계는 **마지막**에 한다. 그 전까지 이중 예약 가능성은 감수 |
| 7 | 공개 범위 | **전 직원에게 제목·신청자 공개** (현행 유지). 사용 목적은 신청자·담당자만 |

## 2. 지금의 정보 표시 방식

### 2-1. 임직원 목록 탭 (테이블 10열)
사진 · 사번 · 이름 · 부서(+겸직 수) · 직급 · 직책 · 이메일(회사/개인 2줄) · 연락처 · 재직상태 · 근태관리

- 필터: 재직상태(전체/재직/발령대기/퇴사자/휴직, 기본 **재직**) · 근태관리(전체/대상/제외) · 부서 · 직급 · 검색(이름·사번·이메일)
- **"사진" 열은 이름 첫 글자 동그라미뿐**이다. `users.photoUrl`을 `profileImage`로 읽어 두고(163행) 화면에서 안 쓴다.
- 정렬 기준이 없다 — `users` 배열 순서 그대로. 업무계획은 이미 `useRosterOrder`(관리자 지정 순서 → 임원 → 부서 → 직책 → 직급 → 이름)를 쓰는데 인명관리는 안 쓴다.
- 근태관리 대상·사번·재직상태 같은 **관리용 열이 일반 직원 화면에도 그대로** 보인다. 주소록으로 쓰려는 사람에게는 소음이고, 관리자에게만 의미가 있다.
- 열이 많아 가로 폭이 좁으면 가로 스크롤.

### 2-2. 회사 조직도 탭
- 왼쪽 부서 트리(📁/📄) + 오른쪽 재직자 카드 그리드.
- 같은 기능의 별도 메뉴 **`조직도`(`OrgChartScreen`)가 이미 있다** → 인명관리 안의 조직도 탭은 중복.

### 2-3. 상세 모달 (행 클릭)
- 왼쪽 프로필 카드(이니셜, 이름, 사번, 부서, 직급·직책) + 오른쪽 탭 2개
  - 💼 인사 및 소속 정보: 부서·직급·직책·입사일·연락처·이메일·겸직 목록
  - 🔒 개인 신상 정보(인사팀용): 주민번호(마스킹 + [전체보기]), 생년월일, 성별, 주소, 개인 이메일, 비상연락처, 학력
- 관리자만: [인사 발령/개인신상 수정], [퇴사 처리]

### 2-4. 모바일
- `MobileContactScreen`: 재직자 연락처 검색·전화 걸기 위주. 데스크톱과 표시 항목·정렬이 다르다.

## 3. ⚠️ 먼저 짚어야 할 문제 — 개인정보 노출

1. **개인 신상 탭에 권한 확인이 없다.** `{detailTab === 'personal' && …}`(1219행)에 `isAdmin` 조건이 없어, 인명관리 메뉴에 들어올 수 있는 **모든 직원이 다른 직원의 주민번호 전체·주소·비상연락처를 볼 수 있다**(마스킹은 [전체보기] 한 번이면 풀림). 탭 이름의 "(인사팀용)"은 안내 문구일 뿐 막지 않는다.
2. **화면에서 숨겨도 데이터는 이미 브라우저에 있다.** `employeeProfileRepo.list()`가 주민번호 포함 전체 프로필을 내려받고, 이 목록을 조직도·근태·연차 화면도 읽는다. 화면 조건만 고쳐서는 개발자도구로 그대로 보인다.
3. `employeeProfiles` 컬렉션은 `scripts/appwrite-schema.ts`에 정의가 없어 컬렉션 권한을 코드로 확인할 수 없다(콘솔 설정 확인 필요).

→ 표시 방식 개편 때 **"누가 어떤 항목을 보는가"를 함께 정하고**, 최소한 1번(화면 차단)은 이번 작업에 포함하길 권한다. 2·3번(서버에서 민감 항목을 빼고 내려주기)은 범위가 커서 별도 과제로 두는 편이 낫다.

## 5. 게시판 현황 (연동 대상)

- 게시판 목록은 코드 고정(`board.seed.ts`): 공지사항 · **경조사(`event`)** · 사내규정 · 자료실. 생일 글은 **경조사 게시판**이 자연스럽다.
- 게시글(`posts`): `id`(작성 시각 문자열), `boardId`, `title`, `content`, `author`(**"이름 직급" 문자열 — 작성자 id 없음**), `date`, `views`, `isPinned`, 첨부.
  - 작성자 판별을 문자열 비교로 한다(492행) → 시스템이 쓴 글의 author를 정하는 규칙이 필요(예: "인사팀" / "WorkFit").
  - 댓글·좋아요가 없다 → "생일 축하 댓글" 같은 상호작용을 원하면 게시판 기능 추가가 필요.
- 글 작성은 화면(`BoardScreen`)에서만 한다. **자동 작성 경로가 없다.**
- 자동 실행 기반은 있다: `appwrite/functions/calendar-reminder`가 cron(5분)으로 도는 Appwrite Function이고, 알림은 `notifications` 컬렉션에 문서를 쓰면 기존 파이프라인(토스트·알림센터·푸시)이 처리한다. 생일 글도 같은 방식(매일 1회 cron Function)으로 만들 수 있다.
  - 브라우저에서 만드는 방식(첫 접속자가 오늘 생일 글을 생성)은 아무도 안 들어오면 안 생기고, 동시 접속 시 중복 위험이 있어 권하지 않는다.

### 생일 계산 규칙 (`birthday/engine.ts`)
- 양력: 그해 같은 날. 2월 29일생은 평년에 2월 28일.
- 음력: 생년월일의 월·일을 그해 음력으로 보고 양력으로 변환. 작은달이라 30일이 없으면 29일. 윤달생은 평달로 본다.
- 음력 12월생은 양력 다음 해 1~2월에 생일이 온다 — `isBirthdayOn`이 전년도 음력까지 본다.
- `birthdaysOn(people, date)`: 그날 생일인 **공개** 대상자. 게시판 연동은 이 함수를 쓰면 된다.
- 테스트: 2026 설날(음 1/1 → 2/17)·추석(음 8/15 → 9/25), 2025 추석(→ 10/6) 등.

## 9. 프로필 설정(`/profile`) 분석과 반영

### 기존
- `src/modules/profile/ProfileScreen.tsx` — 기본 정보(사진, 읽기 전용 이름·사번·부서·직급·직책, **이메일 수정**), 비밀번호 변경, 결재 인증(인감·서명).
- 저장은 `users` 컬렉션만(`userRepo.updateProfile`: email·sealUrl·signUrl·signType·photoUrl). **`employeeProfiles`(연락처·주소·생년월일 등)는 본인이 고칠 수 없었다.**
- 여기서 고치는 "이메일"은 `users.email` = **업무 이메일이자 로그인 ID**(사번 또는 이메일로 로그인). 본인이 바꾸면 로그인 ID가 바뀐다 → 라벨을 `업무 이메일 (로그인 ID)`로 명시(동작은 기존 유지).
- 모바일(`MobileUserMenuSheet`)은 이메일 표시만 있고 편집 화면은 웹 `/profile`.

### 반영 — "인사 정보" 섹션 신설 (`components/MyPersonalInfoSection.tsx`)
- 본인이 등록·수정·삭제(칸 비우고 저장 / 생년월일 [지우기]): **연락처, 비상 연락처, 개인 이메일, 주소, 생년월일 + 음력 + 생일 공개**.
- 저장 경로 `employeeProfileRepo.updateMine` — 허용 항목만 반영(`SELF_EDITABLE_PROFILE_FIELDS`). 소속·직급·직책·재직상태·주민번호·학력·입사일은 관리자만.
- 프로필 문서가 없는 사람은 계정 정보로 새로 만든다. 관리자가 정한 근태 대상 여부는 건드리지 않는다.
- 관리자 수정 창(인명관리 > 인사 발령/개인신상 수정)에도 음력·생일 공개 체크를 추가, 상세의 생년월일 아래에 "생일: 음력 8월 15일 (올해 양력 9월 25일) · 비공개" 표시.

### 운영 반영 전 필요
- `npm run appwrite:schema`로 `birthdaySettings` 컬렉션 생성. 생성 전에는 읽기는 기본값(양력·공개)으로 동작하지만, **프로필 저장 시 생일 설정 쓰기가 실패**한다.
- `employeeProfiles` 컬렉션 권한이 본인 문서 수정을 허용하는지 콘솔 확인(스키마 스크립트에 정의 없음).

## 10. 생일 → 경조사 게시판 자동 게시 권고 (게시판 세션 참고용)

**권고: 매일 07:00 KST에 도는 Appwrite 스케줄 Function**(`calendar-reminder`와 같은 방식), 단 아래를 보완.

1. **하루 1건으로 묶기** — 사람마다 1건이면 같은 날 생일자가 여럿일 때 게시판이 도배된다. "🎂 10월 15일 생일을 축하합니다 — 홍길동 과장(영업팀), …" 한 건.
2. **주말·공휴일 생일은 직전 영업일에 미리** — 07:00 게시를 토·일·공휴일에 하면 아무도 못 본다. 금요일(또는 연휴 전날) 글에 "이번 주말 생일" 로 함께 싣는 방식을 권한다.
3. **중복 방지** — 글 id를 날짜로 고정(`birthday-2026-10-15`)해 함수가 두 번 돌아도 1건. 게시 시점 이후 비공개로 바꾼 사람은 다음 실행부터 빠진다.
4. **대상** — 재직(ACTIVE)·발령 완료자, `birthdayPublic !== false`, 생년월일 있는 사람. 판정은 `birthdaysOn()`과 같은 규칙(Function은 별도 런타임이라 `meeting.js`처럼 규칙 파일을 옮겨 두거나 공용 모듈로 묶는다).
5. **cron** — Appwrite 스케줄은 UTC 기준: `0 22 * * *` (전날 22:00 UTC = 당일 07:00 KST).
6. 작성자 표기(예: "WorkFit" 또는 "인사팀")·상단 고정 여부·고정 해제 시점은 게시판 세션에서 결정.

대안으로 "게시글 없이 대시보드/인명관리에 오늘·이번 주 생일자 위젯"도 가능하다 — 게시판이 쌓이지 않고 비공개 전환이 즉시 반영된다. 게시판 글은 축하 댓글 같은 상호작용이 생길 때 가치가 크다.

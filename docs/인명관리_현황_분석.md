## 2. 지금의 정보 표시 방식

### 2-1. 임직원 목록 탭 (테이블 10열)
사진 · 사번 · 이름 · 부서(+겸직 수) · 직급 · 직책 · 이메일(회사/개인 2줄) · 연락처 · 재직상태 · 근태관리

- 필터: 재직상태(전체/재직/발령대기/퇴사자/휴직, 기본 **재직**) · 근태관리(전체/대상/제외) · 부서 · 직급 · 검색(이름·사번·이메일)
- **"사진" 열은 이름 첫 글자 동그라미뿐**이다. `users.photoUrl`을 `profileImage`로 읽어 두고(163행) 화면에서 안 쓴다.
- 정렬 기준이 없다 — `users` 배열 순서 그대로. 업무계획은 이미 `useRosterOrder`(관리자 지정 순서 → 임원 → 부서 → 직책 → 직급 → 이름)를 쓰는데 인명관리는 안 쓴다.
- 근태관리 대상·사번·재직상태 같은 **관리용 열이 일반 직원 화면에도 그대로** 보인다. 주소록으로 쓰려는 사람에게는 소음이고, 관리자에게만 의미가 있다.
- 열이 많아 가로 폭이 좁으면 가로 스크롤.

### 2-2. 회사 조직도 탭
- 왼쪽 부서 트리(📁/📄) + 오른쪽 재직자 카드 그리드.
- 같은 기능의 별도 메뉴 **`조직도`(`OrgChartScreen`)가 이미 있다** → 인명관리 안의 조직도 탭은 중복.

### 2-3. 상세 모달 (행 클릭)
- 왼쪽 프로필 카드(이니셜, 이름, 사번, 부서, 직급·직책) + 오른쪽 탭 2개
  - 💼 인사 및 소속 정보: 부서·직급·직책·입사일·연락처·이메일·겸직 목록
  - 🔒 개인 신상 정보(인사팀용): 주민번호(마스킹 + [전체보기]), 생년월일, 성별, 주소, 개인 이메일, 비상연락처, 학력
- 관리자만: [인사 발령/개인신상 수정], [퇴사 처리]

### 2-4. 모바일
- `MobileContactScreen`: 재직자 연락처 검색·전화 걸기 위주. 데스크톱과 표시 항목·정렬이 다르다.

## 3. ⚠️ 먼저 짚어야 할 문제 — 개인정보 노출

1. **개인 신상 탭에 권한 확인이 없다.** `{detailTab === 'personal' && …}`(1219행)에 `isAdmin` 조건이 없어, 인명관리 메뉴에 들어올 수 있는 **모든 직원이 다른 직원의 주민번호 전체·주소·비상연락처를 볼 수 있다**(마스킹은 [전체보기] 한 번이면 풀림). 탭 이름의 "(인사팀용)"은 안내 문구일 뿐 막지 않는다.
2. **화면에서 숨겨도 데이터는 이미 브라우저에 있다.** `employeeProfileRepo.list()`가 주민번호 포함 전체 프로필을 내려받고, 이 목록을 조직도·근태·연차 화면도 읽는다. 화면 조건만 고쳐서는 개발자도구로 그대로 보인다.
3. `employeeProfiles` 컬렉션은 `scripts/appwrite-schema.ts`에 정의가 없어 컬렉션 권한을 코드로 확인할 수 없다(콘솔 설정 확인 필요).

→ 표시 방식 개편 때 **"누가 어떤 항목을 보는가"를 함께 정하고**, 최소한 1번(화면 차단)은 이번 작업에 포함하길 권한다. 2·3번(서버에서 민감 항목을 빼고 내려주기)은 범위가 커서 별도 과제로 두는 편이 낫다.

## 4. 생일 관련 현황

- **생일 기능은 아직 어디에도 없다**(검색 결과 0건).
- 생일 데이터: `employeeProfiles.birthDate`(YYYY-MM-DD). 등록·수정 시 비어 있으면 **주민번호 앞 7자리로 자동 계산**(`parseRrnInfo`, 343행)해서 채운다.
  - 주민번호도 생년월일도 없는 사람은 생일을 알 수 없다 → 실제 DB에 몇 명이 채워져 있는지 먼저 확인 필요.
  - **음력 생일 필드는 없다.** 주민번호 기준이라 실제로 지내는 생일과 다를 수 있다.
  - 생일 공개를 원치 않는 사람을 위한 설정이 없다.
- 2월 29일생 처리 규칙이 없다(평년에 언제 축하할지).

## 5. 게시판 현황 (연동 대상)

- 게시판 목록은 코드 고정(`board.seed.ts`): 공지사항 · **경조사(`event`)** · 사내규정 · 자료실. 생일 글은 **경조사 게시판**이 자연스럽다.
- 게시글(`posts`): `id`(작성 시각 문자열), `boardId`, `title`, `content`, `author`(**"이름 직급" 문자열 — 작성자 id 없음**), `date`, `views`, `isPinned`, 첨부.
  - 작성자 판별을 문자열 비교로 한다(492행) → 시스템이 쓴 글의 author를 정하는 규칙이 필요(예: "인사팀" / "WorkFit").
  - 댓글·좋아요가 없다 → "생일 축하 댓글" 같은 상호작용을 원하면 게시판 기능 추가가 필요.
- 글 작성은 화면(`BoardScreen`)에서만 한다. **자동 작성 경로가 없다.**
- 자동 실행 기반은 있다: `appwrite/functions/calendar-reminder`가 cron(5분)으로 도는 Appwrite Function이고, 알림은 `notifications` 컬렉션에 문서를 쓰면 기존 파이프라인(토스트·알림센터·푸시)이 처리한다. 생일 글도 같은 방식(매일 1회 cron Function)으로 만들 수 있다.
  - 브라우저에서 만드는 방식(첫 접속자가 오늘 생일 글을 생성)은 아무도 안 들어오면 안 생기고, 동시 접속 시 중복 위험이 있어 권하지 않는다.

## 1. 배경

업무계획에 회의·미팅을 적으면 캘린더에 공유되는 기능은 좋은 평가를 받았다. 그러나 다음 세 가지가 사용을 방해한다.

| # | 현상 | 원인(현행 구조) |
|---|---|---|
| 1 | "회의록 작성"처럼 **'회의'·'미팅' 글자만 들어가도** 일정이 생긴다 | 본문 키워드 포함 여부로 회의를 판정 |
| 2 | 같은 회의가 **같은 사람 캘린더에 중복** 생성된다 | 동기화 동시 실행 경쟁 + 줄 번호 기반 매칭 |
| 3 | **한 회의에 여러 명이 참여**하면 참석자가 각자 업무계획에 적은 만큼 **캘린더에 회의가 여러 개** 생긴다 | 업무계획 1줄 = 캘린더 일정 1건. "같은 회의"라는 개념이 없음 |

3번은 버그라기보다 **모델의 한계**다. 지금 구조에서 회의는 "각자의 메모"일 뿐이고, 여러 사람이 공유하는 하나의 사건으로 존재하지 않는다.

함께 요청된 고도화: 업무계획 칸을 클릭하면 뜨는 상단 리본에 **굵게·취소선 등 워드 편집기 같은 서식 기능**을 넣는다.

## 2. 상용 그룹웨어·협업툴 선례 조사

### 2.1 회의·참석자 처리 방식

| 제품 | 회의를 어떻게 다루나 | 시사점 |
|---|---|---|
| **Google Calendar** | 주최자 캘린더가 회의 정보를 **소유**하고, 참석자는 같은 ID(iCalUID)의 사본을 받는다. 시간·제목 등 공유 속성은 주최자 변경이 참석자에게 전파되고, 참석자 쪽에서 주최자로 돌아가는 것은 **참석 응답(responseStatus)뿐**이다. | 회의는 **1건**, 참석자는 그 회의에 **연결**될 뿐 |
| **Microsoft Outlook** | 주최자가 초대를 보내고, 참석자가 수락/거절하면 각자 캘린더에 표시된다. 주최자만 **Tracking(응답 현황)** 을 본다. | 주최자 1명 + 응답 추적 |
| **하이웍스** | 일정 등록 시 참여자를 지정하면 **참여자 캘린더에 일정이 표시**되고, 참여자에게 참여 여부를 결정하게 할 수 있다. | 국내 그룹웨어도 같은 모델 |
| **네이버웍스** | 참석자 초대, 참석자 빈 시간 기반 **추천 시간**, 회의실 등 **설비 예약 연동**(빈 설비 자동 탐색), 참석자 자동 알림. | 회의 = 일정 + 참석자 + 회의실 |
| **다우오피스** | 내/관심/부서/전사 캘린더. 일정 등록 화면에서 **회의실(자산) 예약을 한 번에** 설정. 일일·주간 **업무보고**는 HTML5 웹에디터(엑셀·워드 붙여넣기 호환)로 작성. | 업무보고 = 서식 있는 문서 |
| **Flow(플로우)** | 프로젝트의 일정·업무 게시물을 통합 캘린더로 모아보기. "주간회의" 일정에 **참석 버튼**을 누르면 개인 캘린더(구글)에 등록. | 각자 만들지 않고 **기존 회의에 참석** |
| **Google Docs** | `@` 입력으로 사람·날짜·**캘린더 일정 칩** 삽입, `@meeting notes`로 일정의 참석자·제목을 끌어온 회의록 생성. | 문서 안에서는 회의를 **참조(칩)** 로 표시 |
| **Notion** | 회의 DB의 참석자를 **Relation**으로 사람 DB에 연결 → 사람 페이지에서 그 사람의 회의 이력이 자동으로 모인다. | 회의 1건 ↔ 참석자 N명, 각자 다시 적지 않음 |

**공통 원칙**
1. **회의는 한 건이고 주최자가 소유한다.** 참석자는 사본을 만들지 않고 그 회의에 연결된다.
2. 참석자의 개인 화면(캘린더·문서·이력)에는 **연결된 회의가 자동으로 나타난다.** 각자 다시 적지 않는다.
3. 회의를 만드는 행위는 **명시적**이다(일정 만들기·초대·참석 버튼). 본문 단어를 추측해 만드는 제품은 찾지 못했다.
4. 참석자가 주최자에게 돌려주는 것은 **응답(수락/거절)** 정도다.
5. 회의실 예약을 회의 등록과 **한 화면에서** 처리하는 것이 보편적이다.

### 2.2 업무 기록 편집기

| 제품 | 편집 방식 |
|---|---|
| 다우오피스 업무보고 | HTML5 웹에디터, Editor/HTML 모드, 오피스 붙여넣기 |
| Google Docs / Notion | 서식 툴바 + 단축키(Ctrl+B 등) + `@` 칩 |
| Tiptap(오픈소스 편집기) | 굵게 Ctrl+B, 취소선 Ctrl+Shift+S, 형광펜 Ctrl+Shift+H, 체크리스트 Ctrl+Shift+9 등 기본 단축키 제공, 마크다운 붙여넣기 지원 |

## 3. 개선 방향

### 3.1 회의·미팅: "적으면 생긴다" → "회의 1건에 참석자를 연결한다"

#### 핵심 모델
- **회의 = 캘린더 일정 1건** (`eventType: 'MEETING'`, 주최자 소유, `attendeeUserIds`에 참석자).
- 업무계획은 회의를 **복사하지 않고 참조**한다.
- 업무계획 월간표는 이미 캘린더 회의를 **주최자 + 참석자 행 모두에** 칩으로 투영하고 있다(`WorkPlanTeamMonthlyMatrix.tsx` `projectedSchedulesMap`). 그래서 회의를 한 번만 만들면 **참석자 전원의 칸에 자동으로 표시**된다. 새로 만들 화면 요소가 적다.

#### 등록 흐름 (제안)
1. 셀 편집 중 리본의 **[회의 등록]** 버튼(또는 `/회의` 입력).
2. 작은 입력창: 제목, 시간(시작~종료), **참석자 선택**(기존 `CalendarEventModal`의 참석자 선택 재사용), (2단계) 회의실.
3. 저장하면 캘린더에 회의 1건 생성 → 주최자·참석자 칸에 회의 칩 표시.
4. **같은 회의 감지**: 저장 전에 그날 내가 볼 수 있는 회의 중 시간이 겹치고 제목이 비슷한 것이 있으면
   "이미 등록된 회의 ‘주간 정기 회의’(주최 홍길동)가 있습니다. **참석자로 추가할까요?**"를 띄워 **새로 만들지 않고 합류**시킨다. (Flow의 '참석' 버튼과 같은 효과)
5. 칩 클릭 → 회의 상세(시간·참석자·메모). 주최자는 수정·취소, 참석자는 (2단계) 참석/불참 응답.

#### 기존 동작 정리
- 본문 키워드('회의'·'미팅')로 일정을 만드는 **자동 생성은 중단**한다(3.1의 명시적 등록으로 대체).
- 과도기 선택지(§6 d):
  - **A. 즉시 중단**: 새 회의는 [회의 등록]으로만. 가장 깔끔.
  - **B. 태그 줄만 제안**: `[회의]`·`[미팅]` 태그 줄을 저장하면 "캘린더 회의로 등록할까요?" 확인 후 3.1 흐름으로 연결(자동 생성 아님).
- 이미 생성된 업무계획 유래 일정(`[WP-SYNC:…]`)은 그대로 두되 **중복분 정리 스크립트**를 1회 실행(개발 → 운영 순, 별도 승인).

#### 공개 범위와 알림 (§6 b·c 결정용 권고)
선례(Google·Outlook·하이웍스)는 모두 **초대받은 사람에게만** 알린다. 이에 맞춰:
- **보기**: 회의는 전사에서 볼 수 있게(`COMPANY`) — 타 부서 회의 미공개 문제 해소.
- **생성 알림**: **참석자에게만**(초대 알림). 전 직원 알림은 보내지 않는다.
- **10분 전 리마인더**: **주최자 + 참석자**만.
- 구현상 `notifyRecipients`와 `calendar-reminder`가 지금은 `COMPANY`면 전 직원을 대상으로 삼으므로, **"전사 공개이지만 알림은 참석자만"** 이라는 구분(예: 회의 유형이면 공개 범위 대신 참석자 기준)이 필요하다.

### 3.2 업무계획 서식 편집 (리본 확장)

#### 권장안: 텍스트 기반 경량 서식 + 렌더링
| 서식 | 표기(저장) | 단축키 | 표시 |
|---|---|---|---|
| 굵게 | `**텍스트**` | Ctrl+B | **텍스트** |
| 취소선 | `~~텍스트~~` | Ctrl+Shift+S | ~~텍스트~~ |
| 밑줄 | `__텍스트__` | Ctrl+U | 밑줄 |
| 형광펜 | `==텍스트==` | Ctrl+Shift+H | 노란 배경 |
| 글자색(빨강·파랑 등) | `{red}텍스트{/}` | — | 색상 |
| 체크리스트 | `- [ ]` (현행) | Ctrl+Shift+9 | 체크박스 |

- 리본 버튼은 textarea의 **선택 영역을 표기로 감싸거나 해제**한다(토글).
- 편집하지 않을 때 셀은 표기를 **서식으로 렌더링**해 보여준다(태그 칩·체크박스 렌더링과 같은 위치).
- 장점:
  - 저장 형식이 **텍스트 그대로**라 DB 스키마·모바일·검색·체크 메타(`__c__`)·태그 파서가 그대로 동작한다.
  - 새 라이브러리 없음. 렌더링은 정규식 → React 요소 변환으로 처리해 **HTML 주입(XSS) 위험이 없다.**
  - 구글시트에서 옮겨온 "한 칸 = 텍스트" 습관을 유지한다.
- 단점: 편집 중에는 표기 기호가 보인다(완전한 WYSIWYG 아님).
- 주의: `content` 최대 1,000자에 표기 기호도 포함된다. 필요 시 상한 상향 검토.

#### 대안: WYSIWYG 편집기(Tiptap 등) 도입
- 편집 중에도 서식이 그대로 보인다(다우오피스·Notion 수준).
- 대신 저장 형식이 HTML/JSON으로 바뀌어 **파서·체크 메타·모바일·캘린더 동기화를 모두 다시 만들어야** 하고, 의존성 추가와 HTML 정화(sanitize)가 필요하다.
- 권장안으로 먼저 운영해 보고, 표·이미지 같은 요구가 생기면 그때 전환을 검토한다.

## 4. 단계별 실행안

| 단계 | 내용 | 결정 의존 | 규모 |
|---|---|---|---|
| **1. 긴급 안정화** | ① 동기화 planId별 직렬화 + Ctrl+Enter/blur 이중 저장 차단 ② 줄 번호 대신 **내용 키로 기존 일정 수정**(결정 a) ③ 같은 계획 내 중복 일정 자동 정리 ④ **모바일 저장에도 동기화**(결정 e) | 없음 (a·e 결정됨) | 소 |
| **2. 서식 편집** | 리본에 굵게·취소선·밑줄·형광펜·글자색 + 단축키, 셀 렌더링 | 3.2 권장안 승인 | 소~중 |
| **3. 회의 구조 전환** | [회의 등록] 흐름, 같은 회의 감지·합류, 키워드 자동 생성 중단, 알림 대상 분리, 기존 중복 정리 스크립트 | b·c·d | 중 |
| **4. 확장(선택)** | 참석 응답(수락/불참), 회의실 예약 연동(기존 자원예약 모듈 `reservation`에 참석자·시간 필드 있음), 회의 칩에서 회의록 작성 | 별도 | 중~대 |

1단계는 3단계와 충돌하지 않는다. 3단계 전까지 현행 자동 생성이 계속 돌기 때문에, 그동안의 중복을 막는 용도로 먼저 적용한다. 3단계 후에도 "기존 일정 수정·직렬화"는 회의 칩 수정 경로에 그대로 쓰인다.

## 5. 기대 효과

- "회의록 작성" 같은 줄이 일정이 되는 오탐 제거.
- 한 회의 = 캘린더 1건 → 참석자가 몇 명이든 중복 없음. 참석자는 적지 않아도 자기 칸에 회의가 보인다.
- 전사 공개로 타 부서도 회의를 볼 수 있되, 알림은 관계자에게만.
- 업무계획이 서식 있는 업무 기록으로 발전(중요 표시·완료 취소선 등).

### 서식 편집기 설계
- **저장 형식은 줄 단위 텍스트를 유지**한다. 편집기는 텍스트 ↔ 편집기 문서를 변환만 한다. 파서·진행률·모바일·체크 메타를 다시 만들지 않기 위함.
  - 체크리스트 줄 `- [ ]`/`- [x]` ↔ 할 일 항목(체크 상태 보존), 일반 줄 ↔ 문단, 빈 줄 ↔ 빈 문단
  - 인라인 서식 표기: 굵게 `**글**`, 밑줄 `++글++`, 취소선 `~~글~~`, 형광펜 `==글==`, 글자색 `{red}글{/}` (red·blue·green·orange·gray)
- 표시: 편집하지 않는 셀·캘린더 To-Do·모바일에서 표기를 서식으로 렌더링(React 요소, HTML 주입 없음).
- 리본: 굵게(Ctrl+B)·밑줄(Ctrl+U)·취소선(Ctrl+Shift+S)·형광펜(Ctrl+Shift+H)·글자색 버튼 추가, 현재 서식 활성 표시.
- 저장: blur·Ctrl+Enter 유지, 저장 중 중복 호출 차단.

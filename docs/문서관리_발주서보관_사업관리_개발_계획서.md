## 0. 범위

1. **문서관리 — 결재 완료 발주서 보관함**: 전자결재에서 *완료*된 발주서를 별도 보관 공간에 모아 검색·열람·대장 출력.
2. **사업관리 메뉴 신설 → 거래처 정보**: 거래처 마스터(거래처명·사업자번호 등) + 그 거래처와 진행 중인 사업(관련사업명·프로젝트 번호) 조회.
3. **발주서 자동 채움**: 발주서 작성 시 거래처·사업 정보를 마스터에서 불러온다.

- **비대상**: 발주서 양식 자체 — 사용자가 결재서식 관리에서 직접 제작한다. 이 계획은 양식이 쓸 **필드 타입과 보관 연동**만 준비한다.

### 공통 패턴 (우리가 가져올 것)
1. **서식 → 보관함 매핑**: 보관 위치는 문서마다 사람이 고르지 않고 *서식 설정*으로 정한다 (다우오피스 방식). → 발주서 서식에 "보관함 = 발주서 보관함"을 지정하면 완료 시 자동 등록.
2. **문서 메타 = 대장 컬럼**: 문서번호·서식·기안자·기안부서·기안일·완료일·보존연한·보안등급. 대장(목록)과 검색 조건이 이 메타로 만들어진다.
3. **보관함 단위 권한**: 열람/등록/삭제를 보관함 단위로. 결재문서 원본 권한(비공개·보안등급)은 보관함 권한보다 우선한다 — 공유받아도 비공개 문서는 못 본다.
4. **원본 불변**: 보관함은 결재 원본을 *참조*할 뿐 수정하지 않는다. 수정이 필요하면 새 결재.
5. **마스터 참조 서식**: ERP 계열은 거래처·품목 등 마스터를 서식이 참조해 채운다. 상신 시점 값을 문서에 **스냅샷**으로 고정한다(나중에 거래처 주소가 바뀌어도 이미 결재된 발주서는 그대로).

## 3. 설계

### 3.1 사업관리 메뉴 (M_SALES 개편)

```
사업관리 (M_BIZ, 기존 M_SALES 자리)
├─ 거래처 정보        /biz/vendor     ← 신규
├─ 사업 현황          /biz/project    (2차: 전체 사업 목록·거래처별 집계)
└─ 발주서 보관함      /biz/po-archive (문서관리 보관함의 사업관리 바로가기)
```
- 기존 견적·수주 목업 화면은 사용 여부를 사용자 확인 후 `use:false` 처리 또는 유지.
- 권한은 기존 `roleGroup` 화면 ID(S_…) 체계를 그대로 쓴다.

### 3.2 거래처 ↔ 사업 연결

`workProjects`에 **`clientVendorCode`(nullable, FK→vendors.code)** 속성을 추가한다.
- 프로젝트 생성/설정 모달의 "발주처" 입력을 **거래처 선택기**로 바꾸고, 선택 시 `clientName`도 거래처명으로 채운다(기존 리포트 호환).
- 기존 프로젝트(값 없음)는 거래처 정보 화면에서 `clientName`과 거래처명이 **정확히 일치**할 때만 "미연결 추정"으로 회색 표시 → 담당자가 한 번 눌러 연결.
- Appwrite 속성 추가는 **가산 변경**이라 기존 문서는 `null`로 읽힌다 → `fillLegacyProjectFields`에 키 추가.

> 대안: 이름 매칭만으로 처리(스키마 무변경). `대성반도체(주)` ≠ `대성반도체` 같은 표기 차이로 누락되므로 비권장.

### 3.3 거래처 정보 화면 (`/biz/vendor`)

- 좌: 거래처 목록(검색: 거래처명·사업자번호·코드 / 필터: 구분·사용여부)
- 우 상단: 거래처 상세 — 거래처코드, **거래처명, 사업자번호**, 대표자, 업태/종목, 주소, 담당자·연락처, 이메일, 결제조건, 사용여부 (등록·수정 가능)
- 우 하단: **진행 중인 사업 목록** — 프로젝트 번호(`code`), 관련사업명(`name`), 유형(수주·국책 등), 계약번호, 계약기간, 상태, 책임자. 행 클릭 → 업무관리 프로젝트로 이동.
- 사업자번호는 `000-00-00000` 형식 검증(체크섬 포함) + 중복 등록 경고.

vendor 스키마 확장(모두 optional, 가산): `bizType`(업태), `bizItem`(종목), `tel`, `email`, `paymentTerms`.

### 3.4 발주서 자동 채움

결재서식 `FIELD_TYPES`에 두 타입 추가:
- **`거래처`**: 선택기로 거래처를 고르면 거래처명·사업자번호·대표자·주소·담당자를 함께 채운다.
- **`사업`**: 선택기로 프로젝트를 고르면 프로젝트 번호·사업명·계약번호를 채운다. 거래처를 먼저 골랐다면 그 거래처의 사업만 보여준다.

값은 상신 시점의 **스냅샷**으로 `fieldValues`에 저장한다(`vendor.code`, `vendor.name`, `vendor.bizNo`… 평탄화 키). 이후 마스터가 바뀌어도 결재 완료 문서는 변하지 않는다.
→ 사용자가 발주서 양식을 만들 때 이 두 필드를 배치하기만 하면 된다.

### 3.5 문서관리 — 결재 완료 문서 보관함

신규 컬렉션 2개 (기존 `approvalDocs`·`approvalForms`는 **읽기 전용**, CLAUDE.md §2):

```ts
// docArchiveBoxes — 보관함
{ id, name, desc, retentionYears /* 기본 10 */, readerRoleGroupIds[], managerUserIds[], order }

// docArchiveEntries — 보관 대장(원본 참조 + 검색용 메타 스냅샷)
{ id, boxId, docNo /* FK→approvalDocs, 원본 참조 */, formCode, title,
  drafterId, drafterDept, draftedAt, completedAt,
  vendorCode, vendorName, projectCode, projectName, amount,   // 발주서 대장 컬럼
  retentionUntil, archivedAt, archivedBy /* 'system' | userId */ }
```
- **서식 → 보관함 매핑**은 `approvalForms`를 건드리지 않도록 별도 설정(`docArchiveRules`: `formCode → boxId`)으로 둔다.
- **자동 등록**: 문서가 `완료`로 바뀌는 지점에서 매핑된 보관함에 entry 생성. 클라이언트 훅이 놓치는 경우를 대비해 보관함 화면에 "미등록 완료문서 동기화" 버튼(관리자) 제공 — `docNo`가 PK라 중복 등록 없음.
- 열람 시 원본은 기존 결재문서 뷰(`ApprovalDocumentView`)로 열고, 원본의 비공개·권한 규칙을 그대로 따른다.
- 대장: 기간·거래처·사업·기안부서·문서번호 검색 + 엑셀 내보내기.

### 3.6 구현 현황 — 발주서 보관함 (2026-10-20, 1차)

사용자 지시로 양식·거래처 작업보다 **보관함을 먼저** 만들었다. 위 3.5 설계에서 다음을 바꿨다.

- **보관 대장(`docArchiveEntries`)을 만들지 않았다.** 목록은 approvalDocs 구독에서 `완료` + 발주 서식을
  골라 그때그때 보여 준다. 완료 처리 경로(PC·PWA·일괄 결재)에 훅을 걸 필요가 없고, 빠뜨려서 보관함에서
  문서가 사라지는 일이 없다. 결재 문서는 읽기만 한다.
- **발주 서식 판정**: 서식 code 나 이름에 `발주`가 들어 있으면 발주서. 양식을 만들 때 이름을 "발주서"로 하면 된다.
- **회신 문서**만 새로 저장한다 — `poArchiveReplies`(문서당 1건, $id=결재 문서 ID) + 파일은 fileStorage(Garage S3)
  `poArchive/{docId}/`. 다시 올리면 교체하고 이전 파일은 지운다.
- **PDF**: 결재 문서 보기(`ApprovalDocumentView`)를 화면 밖에 그려 이미지로 떠서 A4 PDF로 내려준다(jspdf + html2canvas-pro,
  누를 때만 불러온다). 원본 열람·마스킹 규칙이 그대로 적용된다.
- **열람 범위**: 관여자(기안·결재선·수신)는 언제나, 같은 부서와 문서 관리자(관리자·S_GW_DOCUMENT 등록/수정 권한)는
  공개·일반 등급 문서만. **회신 업로드**: 기안자와 문서 관리자.

| 파일 | 역할 |
|---|---|
| `src/domain/poArchive/schema.ts` (+test) | 발주서 판정·열람/업로드 권한·검색·회신 스키마 |
| `src/data/poArchive/poReply.repo.ts` | 회신 메타 저장 + 파일 업로드/교체/서명 URL |
| `src/features/poArchive/usePoArchive.ts` | 보관함 문서·회신 훅 |
| `src/modules/gw/document/PurchaseOrderArchive.tsx` | 목록(제목·완료일자 / PDF / 회신 문서) + 검색 + 원문 보기 |
| `src/shared/lib/pdf.ts` | 화면 요소 → A4 PDF |
| `scripts/appwrite-schema.ts` | `poArchiveReplies` 컬렉션 정의 |

> 운영 반영 전 `poArchiveReplies` 컬렉션을 만들어야 한다. 없으면 회신 업로드가 오류로 막힌다(조용히 유실되지
> 않도록 첫 등록은 insert). **전용 명령은 이 컬렉션만 새로 만들고, 이미 있으면 아무것도 고치지 않는다**
> (`--only=poArchiveReplies --new-only`; 다른 컬렉션·문서는 조회도 하지 않음, DB가 없으면 만들지 않고 멈춤):
>
> ```bash
> npm run appwrite:schema:po -- --dry-run         # 무엇을 만들지 확인(쓰기 0건)
> npm run appwrite:schema:po                      # dev
> npm run appwrite:schema:po -- --prod            # 운영
> ```
>
> 발주서 판정(서식 code·이름에 '발주')은 실제 발주서 양식을 만든 뒤 고도화한다.

### 3.7 구현 현황 — 사업관리 메뉴 (2026-10-20, 1차)

**영업 관리 숨김·연결 끊기**
- 메뉴 `M_SALES`·하위 3화면 `use:false` → 라우트가 만들어지지 않는다. App 의 화면 매핑(`/sales/*`)도 지워
  견적·수주 데이터(salesOrder·quote)를 부르는 경로가 없다. 코드는 지우지 않고 남겨 두었다.
- 권한 목록(SYSTEM_SCREENS)에서 SALES 카테고리·화면을 빼고 BIZ 로 대체. DB 의 기존 권한 데이터는 건드리지 않는다
  (S_SALES_* 권한이 남아 있어도 메뉴·라우트가 없어 효력이 없다).
- 경영 대시보드의 `/sales/*` 드릴다운 링크 4곳을 끊었다(타일은 그대로, 클릭만 안 됨).
- 기준정보 › 거래처관리(`/base/vendor`)도 숨김 — 같은 vendors 데이터를 사업관리 › 도입기업 정보가 대신한다.

**사업관리 (`M_BIZ`)**
| 화면 | 내용 |
|---|---|
| 도입기업 › 도입기업 정보 `/biz/vendor` | 목록(구분·사용여부·도입기업명/사업자번호 검색, 10/20/50개씩), 신규 등록·수정(코드 자동, 사업자번호 형식·검증번호 경고·**중복 차단**), 상세: 진행 중 사업 목록 + 사업 연결/해제 |
| 사업 관리 › 사업 현황 `/biz/project` | 업무관리 프로젝트를 프로젝트 번호·사업명(계약번호)·유형·도입기업(역할)·기간·**담당자**로. 행 클릭 → 그룹웨어 › 프로젝트 |

- 도입기업-사업 연결은 새 컬렉션 `bizVendorProjects`(역할: 발주처·매입처·외주)에만 저장 — vendors·workProjects 에 칸을 더하지 않았다.
- 프로젝트 발주처명(clientName)이 도입기업명과 같으면(공백·(주) 무시) 연결 전에도 "발주처명 일치"로 보이고 "연결 확정"으로 고정할 수 있다.
- 사업은 업무관리 프로젝트 열람 규칙을 그대로 따른다(볼 수 없는 사업은 안 보임).
- 권한: 그룹권한관리 › 사업관리 카테고리의 `S_BIZ_VENDOR`·`S_BIZ_PROJECT`. 관리자는 자동 통과, 그 외는 부여해야 메뉴가 보인다.

> 운영 반영 전: `npm run appwrite:schema:biz -- --dry-run` 확인 후 `npm run appwrite:schema:biz [-- --prod]`.
> `bizVendorProjects` 만 새로 만들고, `vendors` 는 **없을 때만** 만든다(있으면 조회만). 다른 컬렉션·데이터 무변경.

**2026-10-20 수정**
- 화면 명칭 **거래처 → 도입기업**(메뉴·권한 목록·화면 문구). 내부 ID·URL·컬렉션(`S_BIZ_VENDOR`, `/biz/vendor`, `vendors`)은
  그대로 둬서 이미 부여한 권한이 유지된다.
- **담당자는 사업별** — 도입기업 목록·등록 화면에서 담당자를 빼고, 사업 현황·도입기업 상세의 사업 목록에 **담당자 = 프로젝트 책임자(소유자)**
  를 보인다. 기존 vendors.manager 값은 지우지 않고 보존(화면에만 안 보임).

## 4. 단계

| 단계 | 내용 | DB 변경 |

## 5. 결정 필요 사항

1. **거래처-사업 관계의 의미**: 사업의 *발주처(고객)*만인가, *매입처(우리가 발주서를 보내는 공급사)*도 사업에 연결되는가? 발주서는 보통 공급사에 보내므로, 후자라면 `workProjects` 단일 FK가 아니라 **사업-거래처 연결 테이블**(`projectVendors`: projectId, vendorCode, role=발주처/매입처/외주)이 필요하다.
2. 기존 영업 관리 목업 화면(견적·수주·주문서 현황) 유지 여부.
3. 발주서 보관함 열람 권한 범위(전사 / 사업관리팀·경영지원 / 기안부서).
4. 보존연한 기본값(제안 10년).
